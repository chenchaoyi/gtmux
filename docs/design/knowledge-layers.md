# 三层知识：出厂章程 · 你的守则 · 这台机器的台账

参谋长身上有三处「写着规矩和事实的地方」，它们**看起来都像知识，实际归属完全不同**。
分不清它们，就会出现这样的错觉：把一条本该所有人都拿到的通用改进，留在了一台机器的私有台账里
（2026-09-05 司令就这样问过：「我以为知识库是个性化的本地用户信息，这个看起来是通用的优化建议」）。

这份文档只回答三个问题：**谁写、什么时候进谁的脑子、怎么从一层升到另一层。**

## 三层

| | 出厂章程 `AGENTS.md` | 你的守则 `LOCAL.md` | 这台机器的台账 `knowledge/` |
|---|---|---|---|
| 归属 | **gtmux 产品** | **这个操作者** | **这台机器的参谋长** |
| 谁写 | 代码：`internal/hq/hq.go` 的 `hqInstructions` + `playbook_zh.go` | 你，手写 | 参谋长，边干边记 |
| 怎么更新 | 改代码 + 升 `hqPlaybookVersion` → 随 `gtmux update` 下发，重新生成 | 你自己编辑；**gtmux 永不覆盖**（种一次） | `gtmux knowledge add/supersede/retire`，追加式台账 |
| 何时生效 | **每轮会话都在上下文里** | **每轮会话都在上下文里**（`AGENTS.md` 末尾 `@LOCAL.md` 导入） | **按需**：派活时按仓库名/关键词回声 `pitfalls`+`workflows` 给 worker；其余靠参谋长主动查 |
| 进谁的脑子 | 参谋长 | 参谋长 | 主要是 **worker**（派活回声）；参谋长是查阅者 |
| 形态 | 一份被管理的文档，不可手改 | 一份你的文档 | 一本带出处的台账（可 supersede、可退休、有审计） |

**导入顺序是有意的**：`AGENTS.md` 的正文在前、`@LOCAL.md` 在最后 —— 你的守则**扩展并覆盖**出厂章程。
不认同某条出厂规矩，在 `LOCAL.md` 写一句压过去即可，不必改代码。

## 一句话判据

- **「我希望你以后都这样做」** → `LOCAL.md`。它每轮都在场，是你对参谋长的权威。
- **「我发现了这个坑 / 这条流程是这样的」** → 知识库。它是事实和教训，用的时候才需要浮出来。
- **「这条规矩每台机器都该有」** → 出厂章程，也就是**改代码**。

第三条是最容易漏的那条，因为它看起来和第二条一样都是「一条经验」。区别在于**它是否与这台机器有关**：
「wrangler 在办公网会 TLS reset」是这台机器的事；「派活前要显式选 model，别继承上次的」是所有人的事。

## 从台账升到章程：promote → land

台账是**本机私有**的，但它会长出「比这台机器大」的条目。那条出口是机械的，不靠记性：

1. 参谋长判断某条够 **charter 级** → `gtmux knowledge promote <id> --why … [--target …]`
2. gtmux 在 `knowledge/promotions/` 写一份**带走简报**：教训原文、为什么升、建议落点、完整出处
3. **人把它搬到那个持久载体** —— 这一步机器做不了，是整条生命周期里唯一卡在人身上的
4. `gtmux knowledge land <id> --ref …` 关闭闭环，简报删除，台账保留全过程
5. `gtmux doctor` 盯着这个队列：**超过约两周没带走的会被标出来**

**落点可能是哪几种**（这决定了第 3 步该干什么）：

- **`LOCAL.md`** —— 这条规矩只管你自己的参谋长
- **某个项目的 `AGENTS.md` / `CLAUDE.md`** —— 只管那个仓库
- **团队 runbook** —— 只管你的团队
- **gtmux 自己的仓库** —— 所有人都该拿到：改 `hqInstructions`（两份语言都要改）并**升 `hqPlaybookVersion`**，
  否则已存在的 HQ home 收不到

> 已知缺口（2026-09-05）：**上面这四种落点只存在于 `--target` 那句自由文本里**，数据层面没有字段区分。
> 于是「哪些该进代码」只能靠参谋长写清楚、人读明白，机器筛不出来。给 `promote` 加一个载体类型
> （`local` / `project` / `team` / `gtmux`）是把它变成可判定的最小改动 —— 尚未决定是否要做。

## 三层之外：候选池

`gtmux capture "<一句教训> @<topic>"` 是**成本最低的入口**：worker 干活时随手记一句，落进
`knowledge/.pending-distill.jsonl` 的候选池，**不是**台账条目。参谋长的 distill 过程是质量闸门 ——
把同 key 的候选合并成一条正式条目（`knowledge add --capture <key>`），或者带理由驳回
（`knowledge dismiss --why …`，驳回同样留痕）。

写条目要正文，所以 `add` / `supersede` 只在 CLI 上；手机和菜单栏只做**判断型动作**
（promote / land / retire / dismiss）—— 在手机上敲正文，正是知识库长满没人愿读的条目的方式。
