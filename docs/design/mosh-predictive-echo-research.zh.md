# Mosh 对 gtmux 的评估 —— 预测式本地回显（2026-07-22）

接 `remote-attach-research.md`。对照 gtmux 的远程面（`attach` WS 桥 + 移动端终端）评估
https://mosh.org，判断有哪些能直接用、哪些值得重新实现。起因是它「消除网络延迟」的说法：

> "SSH waits for the server's reply before showing you your own typing… Mosh gives an
> instant response to typing, deleting, and line editing… On a bad connection,
> outstanding predictions are underlined so you won't be misled."

## Mosh 到底做了什么（4 根支柱）

1. **预测式本地回显。**客户端假设每次按键会在光标处回显、退格/←/→ 做显而易见的事；
   预测**只在高延迟下**显示，**未确认的加下划线**，遇到会改变状态的键（ESC/CR/方向键）就重开一个
   「epoch」（暂停预测）。预测**只画在本地** —— 服务端输出是权威、会覆盖 —— 所以在 vim/emacs 里也安全。
2. **漫游 / 休眠。**UDP 数据报带递增序号 + 3s 心跳；服务端只要收到更高序号的包就把回复地址切过去
   → 扛得住换 IP / NAT / 休眠。「好久没收到服务端消息」时给出警告。
3. **SSP（状态同步协议）。**同步的是**屏幕状态快照的 diff**，不是字节流 —— 跳过中间帧
   （`yes` 洪水淹不了你），调节帧率避免缓冲膨胀，Ctrl-C 始终即时。两条 SSP（按键上行，屏幕下行）。
4. **传输 = UDP** + AES-128-OCB3。

## 我们面对的两条硬约束

- **传输不匹配。**Mosh 是 UDP；gtmux 整套远程方案是**穿隧道的 WS/TCP**，正是为了穿过封 UDP 的
  NAT/企业防火墙（mosh 需要 UDP 60000–61000 开放 —— 办公网络丢的就是这个）。
  **我们既不能封装也不能采用 mosh；它的传输层恰恰是我们的隧道运不了的。**
- **许可证。**Mosh 是 **GPLv3** —— 抄它的代码会把 gtmux 拖成 GPL。可以**参考设计、干净地重新实现**；
  算法有完整文档。

## 逐支柱裁定

| Mosh 支柱 | gtmux 裁定 |
|---|---|
| **预测式本地回显** | ⭐ **重新实现（参考设计）。**唯一高价值的借鉴 —— 也是唯一能让跨网打字*感觉*即时的 gtmux 侧改动。适用于 **`attach`**（逐键的那个面）—— 不是移动端；见下文「更正」。 |
| **漫游** | 只借*思路*：WS 心跳 + 快速重连并重绘（tmux 保着会话）+ 「好久没收到服务端消息」警告。不借 UDP 机制。作为 `attach` 韧性的后续项。 |
| **SSP 屏幕 diff** | **移动端已经白得了** —— 移动端终端每 ~1.5s 轮询一次 `capture-pane`（整个当前屏幕），也就是它同步的本来就是*屏幕状态*而非字节，天然继承 mosh 的抗洪水能力。对 `attach`（字节透传）而言，完整 SSP = 重写（推迟的「档 2」），不值；我们的同步写背压 + 独立输入 goroutine 已经限住内存、保住 Ctrl-C 的响应。 |
| **坚持 UTF-8** | 已经学到了 —— 我们强制 `LC_CTYPE` + `tmux -u`（见 `attach-cjk-term-locale`）。 |

## 为什么这个修法是真的（回顾我们的延迟发现）

2026-07-21 的诊断：attach 的逐键延迟约 **340 ms**，那是**经跨境 VPN 到海外 VPS 的物理往返** ——
不是 gtmux 代码的问题。网络/基础设施的修法（优先走局域网、更近的 VPS、修掉代理 fake-ip 多出的
5 s 假 TLS）能降 RTT，但抹不掉距离。**预测式本地回显是唯一能在 340 ms *之下*让打字感觉即时的
gtmux 侧杠杆** —— 它把常见情形（在提示符下打字）的 RTT 藏起来，同时保持诚实（下划线）和权威
（服务端说了算）。这正是 mosh 的价值所在，而且与传输层无关，所以在我们的 WS/TCP 隧道上也成立。

## 更正（2026-07-22）：「移动端优先」是错的 —— 目标是 `attach`

这份笔记的初版建议先在**移动端**上预测式回显，理由是移动端终端已经有裸 `attach` 客户端缺少的
光标/屏幕模型。动手实现时，这个前提垮了：

- **移动端输入是批量的编辑框，不是逐键的。**自由文本打进 RN 的 `TextInput` —— 它**本来就在
  本地即时回显** —— 然后 Send 带 `enter: true` 把整串提交（`Composer.tsx`）。没有逐键进入 pane 的
  路径；控制键（Tab/Enter/Ctrl-C/Esc）和 1/2/3 审批各自只发一个键，而且都是**状态变更**
  （mosh 说：绝不预测穿过这些键）。所以 mosh 式的逐键本地回显在移动端**无处可插** ——
  它要修的东西（等一次往返才显示的打字）根本不发生；编辑框本身就是回显。
- **真正疼的面是 `attach`** —— 一个裸的、逐键的终端客户端，每个字符都要等完整一次往返
  （实测 ~340 ms）。但 `attach` 是 **Go** 客户端（`internal/connect/attach.go`），移动端/TS 的
  预测器帮不上它；而且如最初的 `remote-attach-research.md` 已指出的，它没有客户端侧的终端状态模型。
  要在那里做预测式回显，Go 客户端得**内嵌一个 VT 解析器**才知道光标和当前行。

所以预测式回显在两个面上**都不是快赢**：移动端不需要（批量 + 本地已回显），`attach` 得先有真正的
VT 模型。这又绕回 `remote-attach-research.md` 当初把预测式回显推迟的同一个理由。

## 可借的启发式（直接来自 mosh，重新实现）

- **只预测可打印字符 + 退格**（本地光标前进 / 后退）；愿意的话把 ←/→ 当光标移动，
  但 **ESC / Enter / 其他一切 = 结束 epoch**（停止预测，直到服务端确认）—— 绝不猜穿状态变更。
- **自适应：**测量发送往返；低延迟时（局域网 / 快隧道）**完全不预测**（无下划线、无风险）。
  只在超过阈值（几十 ms）时才启用。
- **未确认的预测加下划线 / 变暗** —— 视觉上诚实；猜错会在一个 RTT 内被权威的 capture 纠正，
  最坏只是短暂闪一下。
- 预测**仅限本地显示** —— 真正的按键仍走 `POST /api/send`；功能和服务端的权威性不变。

## 建议（已更正）

预测式本地回显仍是 mosh 里唯一值得的想法，但它唯一真正的归宿是 `attach`（Go），而且只能作为
**一项较大的工作** —— 裸客户端要先内嵌 VT 模型才知道光标/当前行，然后才是可借的启发式
（预测可打印 + 退格、未确认加下划线、快链路上自适应关闭、状态键重置 epoch、仅本地 + 服务端权威）。
它**不是**快赢，也**不是**移动端功能。既然 ~340 ms 根本上是海外 VPS 的距离，更便宜、更高杠杆的
修法仍然是：在网内时**优先直连局域网**、**更近/更快的隧道 VPS**、修掉代理 fake-ip
（全是网络/基础设施，不动代码）。只有当跨网 attach 打字必须即时、且这些都用尽时，才做 `attach`
的预测式回显。

另有一项值得单独小做的、无论如何都该做的事：`attach` 在 WS 断开时的**重连/重同步**
（tmux 保着会话；重新 attach 即重绘）+ 「好久没收到服务端消息」的警告 —— 这是 mosh 漫游里
可借的部分，不需要 UDP。**不要**采用 mosh 本身（UDP 是我们的隧道运不了的；GPLv3）。
