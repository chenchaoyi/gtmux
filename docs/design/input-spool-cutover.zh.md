# 共享输入队列换代与容量验证

## 初始条件

v1.0.185 的 Go 发起方和接收方通过 `terminal-input/` 访问原文件队列。旧 Go 在已有项数恰为 4,096 时仍可创建请求；回执写入也不使用新版结算租约。仅观察空句柄或持有新版租约，不能证明旧版回执已经排空。

现有候选保留 v1 JSON 版式。真实只读样本有 3,168 个名字和至少 1,347 个回执预留，合计至少 4,515 槽。4,096 上限无法在该样本接纳新请求。未决、未知以及仍在保留期的回执继续保留。

## 选择的切换

1. 先停止接入新发送，让旧 Go 和 DSH 所有在途传输到确定边界。核对服务、CLI 入口和进程版本，等待已确认的回执持久化。不能证明结局的 claim 保持未知，禁止重放。确认旧进程不持有队列目录 fd、正在写的配套文件或已提交未回执的操作。结算端没有纳入共享租约，这一步不能以抢到租约替代。
2. 在相同受管父目录创建 owner-only 的普通文件作为版本标记。验原路径是受管目录、目标路径是准备好的标记、两者同设备且无符号链接。用平台原子交换将旧目录移到 `terminal-input-v2`，将普通文件留在 `terminal-input`。任何不支持交换、管理员权限不符或身份不确定的情况均保持拒写。沿用同一个目录 inode 和所有 v1 文件，避免复制、跳过未知记录或重新编号。普通文件还应绑定布局与期望的新目录身份；恢复流程须保留这一事实。
3. 新进程只在布局切换被确认且版本标记匹配后启动。旧 Go 的固定路径此时无法用于 Prepare、Claim、Finish。旧 DSH 插件也固定读旧目录，因此实际放行前要更新接收器并验证它使用同一代的目录。暂不允许两代写入者都使用一个可写目录。读回执、领取、结算、扫描和清理必须统一使用当前的目录身份。
4. 首轮试算使用 6,144 槽，为 4,515 槽的样本预留结算及新请求；按原规则单次新动作至少要三槽。最终值应由精确的切换前计数和磁盘测量确认。若引入本机 owner-only 配置，默认保留 4,096，新代才允许有界覆盖，拒绝非法值并保持扫描上限独立有界。配置不下发给手机、浏览器或旧进程。队列格式依旧 v1，1 MiB 正文及 JSON 文件既有读限沿用。槽位上限与目录总字节配额是不同约束。

## 验证矩阵

- macOS 私有夹具用实际原子交换，证明目录 inode 和完整文件指纹不变。用 v1.0.185 的固定 Go 源码执行迟到的 Prepare、Claim、Finish，逐项拒绝且原目录中无新增、回执不被覆盖。
- 同一夹具合成 3,168 个文件、1,347 个预留（4,515 槽）。固定候选使用私有测试 overlay 指向新路径并设 6,144，使用真实候选 Prepare、Claim、Finish 证明可以接纳新 ID、完成原 pending 的结算，保留另一未决、未知、去重和旧接受回执；矛盾结局被拒。
- 仍需验证实际写入方排空、新 DSH 的协议选择、持久切换标记及异常恢复、容量配置的范围和授权，以及正常本地和远端门禁。出现切换后写入时，不能把目录盲目交换回去让旧代码重新获得发送权限。回退只能先停接入、对账、核对所有代际写入者，保持未知没有新的发送权。真实目录未参与此设计实验。
