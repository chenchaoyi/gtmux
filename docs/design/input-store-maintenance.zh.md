# Terminal 输入队列生产预检与维护

当前候选为 Go 与 DSH 的共同队列门禁，基于 `d6a8a418b89a1c5ecf7007fa9728600888a80f63`。运行中的 v1.0.185 使用原 `terminal-input`。候选在原布局兼容 v1，只有有效的激活记录、原路径标记和目录身份同时匹配才选择 `terminal-input-v2`。准备、领取和结算仍用 v1 JSON，Go 在内存绑定代次，新 DSH 在注册、就绪和提交前复核代次。`prepared`、`rolling-back`、缺失或不一致的切换信息会拒写。候选没有维护停接开关或生产激活、恢复写入工具。 [共同门禁设计](input-store-gate.zh.md) · [原子交换及恢复证据](input-spool-cutover-recovery.zh.md)

## 只读预检

在该实例所属用户下执行。不要改用 `sudo`，否则归属检查将采用不同用户。脚本只读取给定根的类型、权限、切换元数据、文件名分类、逻辑／分配字节和 DSH 就绪记录。输出不含正文、请求 ID 或代次 token。`legacy`、`fresh`、`active` 表示观察到的布局。退出 2 或 `unverified` 需核对证据。退出 0 时 `maintenance_ready` 仍为 `unverified`。目录项计数可用于估算盘点成本，容量与回执完整性须按有效 v1 索引、领取及回执另做对账。正在运行的队列可在两次扫描之间变化。

```sh
state_root="$HOME/.local/share/gtmux"
python3 -B docs/design/input-store-preflight.py "$state_root"
df -k "$state_root"
command -v gtmux
gtmux --version
```

同时查询本用户 launchd 的 `com.gtmux.serve`、`com.gtmux.selftunnel`、`com.gtmux.tunnel`，只留状态和 PID。用 `ps` 建立进程及父进程清单，保留 PID、启动时间、程序来源、实例标识。用 `lsof -nP -a -p <PID> -iTCP -sTCP:LISTEN` 核监听，用 `lsof -nP -Fp +D <队列路径>` 或有界等效工具核句柄。扫描前核目录规模，覆盖原、新目录、标记、租约、暂存和已取消链接的句柄；查看已知写入进程所持的目录或同设备 inode。权限、超时及命令退出原因要分开记录。无匹配只是当前采样无结果。进程现场命令行、服务参数可能含凭据，只保留经筛选的字段。已安装二进制或 `bridge.mjs` 的哈希不能证明当前进程载入了同一版本。

## 维护窗口流程

1. **确认范围和角色。** 维护协调者确认准确实例、所有入口及其所有者、目标 Go 和 DSH 版本、最新可用空间、停接范围、恢复责任人和独立验收人。两条写入路径都要有可验证的停接和排空方式。当前只读预检不能签发维护就绪。低于 8 GiB 先报告并暂缓下一项高写入检查，已经运行的检查自然结束。
2. **停接后排空。** 入口所有者暂停新的 CLI、自动化和 HTTP／终端输入并阻止旧接收器重新拉起。使用有界维护窗口，允许停接前已进入的处理链继续生成回执。保存各入口停接确认、拒绝新请求的指标或已批准的控制探针结果、停接时间、进入清单和完成时间。复核 WebSocket、后台自动化及现存本地 shell。同一时期反复核对活跃请求、进程 PID／出生时间、打开的文件与目录 fd，包含辅助进程。先确认旧写入者已正常结束，或所有写入入口和持有权均已释放且不能重取。瞬时 `lsof` 无结果、固定睡眠或持有新租约均不能代替这一步。任何实际入口或句柄无法认领时维持停接，暂缓交换。
3. **核对回执及持久性。** 按原请求 ID 和目的地对账，记录索引、待发、领取和已接受回执。已接受保留作去重，结果未知保留原索引和领取记录并拒绝自动重放。未启动的待发保留；仍有处理者在工作时继续等，不能换代。检查读回的内容和文件身份，记录原目录设备/inode，按批准范围保留恢复副本或校验清单。现行 Go `atomicPrivate` 和 DSH `atomicJSON` 写完后原子改名但没有显式同步调用。文件可读、API 已响应或目录列表稳定，只能证明本次观察可见。生产激活前应由维护工具和指定操作人对关闭写入后的回执、队列目录、切换记录及父目录做适用的同步，记录每步结果，并验证宿主重启／断电后的实际恢复。任何同步或对账失败保留原文件和停接状态。 [Go 回执写入](../../internal/agentclient/delivery.go#L202) · [DSH 回执写入](../../internal/app/dsh_terminal_plugin.mjs#L32)
4. **同一责任人准备、交换和激活。** 只在停接和排空已核准后，指定的队列维护人使用审过的工具发布持久 `prepared` 记录；在同一文件系统原子交换原队列和私有普通文件标记。确认原目录 inode 在新路径、旧路径成为单链接标记、两者与记录绑定且旧写入者仍然关闭。按工具的持久化协议同步交换和上层目录，再发布并读回持久的 `active` 记录。隔离实验证明旧 Go `Prepare`、`ClaimNative`、`FinishNative` 和已测旧 DSH 的新打开会被普通标记挡住。早先打开的目录或文件 fd 可以越过改名写入旧 inode，依赖第 2 步关闭。新版布局检查和旧路径标记都不能替代对保留句柄的核对。
5. **同代启动后再开放入口。** 激活者保留停接，主机服务所有者启动已验证的新 Go 和新 DSH。启动顺序可由服务所有者选择，DSH 流量应等同代就绪证据出现后才开放。对照实际进程版本、布局身份、接收器代次、稳定 ID 与回执，并用经批准的验证证明旧路径仍拒绝，且原未决、未知、已接受三类可辨认。独立验收人确认服务、回执和身份一致后，协调者逐项恢复入口和调度。失效保持拒写，保留证据与数据。

### 重启与回退责任

| 看到的状态 | 由恢复操作人处理 |
| --- | --- |
| `prepared`、未激活或回退中 | 保持停接并证明还没有开放过新一代写入。按固定记录和路径身份选择继续激活或重复可恢复的回退步骤。回退完成需确认原 inode、v1 内容及回执对账，随后由原版本服务所有者按签发范围启动。 |
| `active` 已持久化，或新一代曾可能写入 | 保持发送停接并沿当前代向前恢复，校验原目录、标记、记录、回执和新 Go／DSH 同代就绪。服务所有者只启动经认定的匹配版本。禁止自动把旧程序重新接回原路径。向旧版降级需要另行排空并核对兼容性、容量和去重。 |
| 记录缺失、损坏、身份冲突或提交结果未知 | 保存两个路径和原日志，暂缓开放。指定恢复操作人从维护记录及恢复材料核对，独立验收人确认后再由协调者决定。不要凭时间、文件名或空目录猜测代次。 |

## 容量和接入门禁

生产准入保持 4,096 个有效槽，目录扫描保持 8,192 项。此前 4,515 槽样本由 3,168 个物理目录项和 1,347 个预留槽组成。试验限额 6,144 下新 ID 和原请求结算都通过，剩 1,629 槽。试验同时扩大了派生扫描上限，不能为扩大生产扫描提供依据。若确需过渡，先评审本机所有者配置上限、期限和单独扫描边界；需计索引、待发、领取、已接受、未知保留及暂存文件的序列化和磁盘分配，为已准入请求留结算空间。1 MiB 正文上限不能作为队列总字节预算。这个候选未调整默认或提供过渡配置。 [现有准入和扫描](../../internal/agentclient/spool.go#L12)

正式接入仍需验证入口停接与在途排空的真实实现、同步及故障恢复工具、实际重启顺序和在另一环境做断电验证。当前候选需完成准确差异独审、受影响套件、正常 CI 与发行门禁。只读脚本的夹具结果仅覆盖观察工具，不扩大原 Go／DSH 定点验证的范围。
