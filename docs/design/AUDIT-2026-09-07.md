# 代码体检 · 2026-09-07

一次全仓审计的记录：死代码、架构与模块边界、内聚与耦合、注释是否还说真话、测试是否有冗余或
重大缺失。**结论按证据写，没量到的不写。** 当场修掉的已经标注，留作建议的写清为什么没在这一轮动。

## 规模

Go 侧 48.9k 行实现 + 35.7k 行测试，比值 **0.73**。按包看，测试密度最低的三个是
`internal/app`（0.50）、`internal/connect`（0.44）和 `internal/ghostty`（0.53）。

语句覆盖率（`go test -cover`）：多数包在 76%–100%；明显偏低的是 `internal/app` 29.3%、
`internal/servermode` 31.0%、`internal/tabalert` 30.2%、`internal/connect` 39.6%、
`internal/ghostty` 42.0%。这几个包的共同点是**大部分代码在跟外部世界打交道**（终端 AppleScript、
launchd、WebSocket 终端透传），单测能覆盖的比例天然低；把它们的数字硬拉高会写出一堆
mock 自己的测试。这不是「要补到 80%」的清单，是「知道哪里没有网」的地图。

## 死代码

`deadcode -test ./...` 全仓只报出 **3 个**不可达函数（`mobileapp/node_modules` 里的第三方
Go 包不计）。对 49k 行来说这非常干净。三个都已删除，因为它们各自还带着一段**已经不成立的注释**：

- `dispatch.DraftOf` —— 注释说「HQ 的草稿守卫用的就是它」，而守卫早已换成
  `dispatch.BoxEmpty` / `DraftOfColored`。留着它不是方便而是陷阱：普通 capture 会把 SGR faint
  标记洗掉，Claude 的暗色幽灵补全就会被读成用户草稿 —— 那正是 v0.46.2 「每次发送都说有人在输入」
  的 bug。删掉它，问草稿的人只剩一条正确的路。
- `connect.Client.Base` / `.Token` —— 注释说「用来拼 WS attach URL」，而 `RunAttach(base, token, …)`
  早就直接收字符串，这两个访问器从设计变更那天起就没有调用者。

## 架构

**包依赖是无环的，方向也守住了**：`app → hq → {radar, dispatchbridge} → 叶子`，`hq` 从不 import
`app`。`scripts/check-design.sh` 在 CI 里守这条线。

一个值得说出来的**好设计**：`internal/server` 只依赖 3 个内部包（`connect` / `prompt` /
`terminal`）。它需要的雷达、digest、usage 数据不是 import 来的，是调用方以函数值注入的
（`server.Deps`）。所以 HTTP 层不认识业务层，也就不可能把业务层的循环拖进来。

**要留意的一处**：`internal/hq` 正在长成第二个大包 —— 8.2k 行、扇出 24 个内部包，仅次于
`internal/app` 的 29。它里面 `knowledge*.go` 六个文件 2.7k 行（占该包 33%）是一个边界清楚的
子域，而这个仓库已经有现成的拆分惯例：`hqnudge` / `hqwake` / `hqpane` / `hqsurface` 都是从 `hq`
分出去的兄弟包。**建议下一次动 HQ 时把它拆成 `internal/hqknowledge`**，不建议为拆而拆地现在
就做：这一轮的改动都在发版路径上，纯搬运会把 diff 冲淡到没人能审。

`hq.go` 1774 行看着吓人，但它只导出一个函数（`CmdHQ`），且 **38% 是反引号里的章程与种子文本**，
不是逻辑。它是「一个命令 + 它的私有辅助」，内聚是好的，只是数据和代码住在一起。

## 注释是否偏移

写了个脚本把注释里出现的仓库内路径全部对照文件系统检查了一遍：**没有指向已删除文件的引用**
（报出来的 `api/agents` 之类全是 HTTP 路由，不是路径）。

真正的偏移是另一类，脚本抓不到：**注释描述的机制已经换掉了**。本轮抓到的三处都在上面「死代码」
一节 —— 它们同时是死的和过时的，这不是巧合：没有调用者的代码也没有人会去更新它的注释。

## 测试

**没有发现明显冗余**的测试。抽查未见「断言常量等于自己」或纯 fixture 复读的用例；重复出现的
是同一条规则在不同层各钉一次（例如状态色在 Go、Swift、TS 三端各有一致性断言），那是跨端契约的
必要重复，不是冗余。

**一处重大缺失已补**：`internal/panefocus` 是全仓唯一 0 覆盖的包，而「跳到某个 pane」正是菜单栏、
手机、浏览器镜像和 `gtmux focus` 四个入口共用的那个动作。补了三条测试，覆盖没有 tmux 时不 panic、
以及 `POST /api/focus` 的**入参校验** —— 顺带发现 `paneIDRe` 只锚了开头没锚结尾，`%12x` 会通过
校验再以「pane 不存在」失败，等于回答了另一个问题。已封尾。（不是安全问题：tmux 一律走
`exec.Command` 分离参数，从不过 shell。）

## 本轮没做、且故意没做的

- 不为覆盖率数字给 `app` / `connect` / `ghostty` 补测试。这些包的未覆盖部分是真实的外部交互，
  补出来的会是 mock 在自证。
- 不拆 `internal/hqknowledge`。理由见上：纯搬运的 diff 会淹掉同批的行为改动。
