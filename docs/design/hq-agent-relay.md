# Agent → HQ relay (v1)

`gtmux relay report|ask` records an agent-authored request under the gtmux state directory. The caller's live `TMUX_PANE` determines its source; tmux supplies the session name and pane PID, and the dispatch ledger supplies the task ID. The CLI accepts a caller-supplied request ID for retry. A repeated ID with identical content and source returns the existing record; a changed payload or source is refused. The record is committed before a wake is queued. Reports are nonblocking by default; `--blocking` also wakes HQ. Questions are blocking unless `--nonblocking` is set; `--for user` always makes the request blocking. The wake names the ID, source and kind, with a command to read the record. HQ reads `gtmux relay list/show`, claims a request, then replies or closes it. The wake is a hint, not the queue.

Each JSON file has one request and its state (`pending → claimed → replied|closed`). File updates take a process lock, sync the file, rename it and sync the directory, so concurrent CLIs cannot claim twice or expose half a record. A claim can be reclaimed after five minutes. This does not invalidate a later reply or close: the record stores the claim time, not a claimant identity. A reply is recorded before delivery. If delivery fails, HQ can explicitly retry with `gtmux relay retry <id>`; relay does not run an automatic retry loop. The `delivered` field means the dispatch layer confirmed delivery **or saw on screen that the agent queued the message behind its current turn**; it is not an acknowledgment that the agent read or acted on the reply. The injected text is explicitly labeled as an HQ reply to an agent request, and the existing send audit marks HQ as its author. Relay has no direct agent-to-agent route; `gtmux send` is a separate command.

Before delivery, relay checks the pane ID, tmux session name and pane PID against the saved source, and refuses a pane whose current command is a known shell or `gtmux`. If these checks fail, the reply stays in the ledger. These are pane-lifetime checks. The pane PID usually belongs to its shell, so they do not detect a replacement agent process or a new conversation in the same pane. The command check is also not an agent allowlist: it only excludes known shells and `gtmux`. The managed machine-knowledge block gives Claude, Codex, opencode, and Kimi a short global relay note after a successful `gtmux knowledge sync`; newly started sessions load it. Other agent types learn the entry point from a new interactive `gtmux spawn` dispatch. Existing conversations must reload their instructions or use `gtmux relay --help`. HQ's managed playbook names the pull/claim/reply flow and the permission boundary. Requests addressed to the user cannot receive an HQ reply: the user answers in the source pane, after which HQ can close the record. HQ may relay other questions to the user, but cannot grant a user-specific permission, choose a user-reserved plan, or authorize an irreversible act. One-shot jobs have no live reply composer and remain outside the reply path in v1.
