# gtmux 整体能力评估

[English](capability-review.md) · **中文**

## 1. 范围与现有基础

基于 `c7c7c301` 与 mobile-new-session 分支，检查日期为 2026-10-01。范围覆盖整个产品，不限手机界面。下列建议未在本轮实现；本轮不发版安装。模拟器验证不能代替解锁后的 iPhone/iPad 真机验收。

| 产品领域 | 已有基础 | 值得补全的方向 |
|---|---|---|
| agent 观察 | 雷达、digest、driver 事实与读屏回退、tmux/native/桌面会话区分 | 状态能解释，误判能复现 |
| 工作控制 | send/focus/attach、spawn/reap、worktree、模型选择；手机新建 shell | 按项目开工，交付后能验收 |
| HQ | 唤醒与 watchdog、持久化 relay、待决事项、章程与 LOCAL.md | 授权范围可见，任务结果可追踪 |
| 知识库 | 候选台账、出处、落地、词法检索、分发、导出迁移 | 证明召回的经验确实帮助工作 |
| 连接 | owner/guest、线路、多台已存 Mac、按 Mac 配置推送 | 跨 Mac 统一待办，功能不可用时说明原因 |
| 连续性 | resurrect、agent resume、CLI 选择与预览恢复、档案迁移 | 项目工作集与清楚的恢复预览 |
| 运维 | 结构化日志与事件、doctor 包、资源与用量监控 | 状态纠错入口，操作能追到结果 |

## 2. 按价值排序的机会

### P1 — 状态判断可解释，误判可纠正

**证据：** `internal/driver/driver.go` 已区分确认事实与回退信号，`internal/radar/digest.go` 已有感知层级，`internal/radar/agents.go` 支持读屏回放。不是缺少状态引擎，而是用户很难知道它为什么这样判断。此前 warning、桌面会话与 HQ 的反复误判，说明这项基础能力价值很高。

**首批：** 在会话中显示状态依据、观察时间和是否过期；增加「状态不对」入口，截取有限、脱敏的证据窗口，写入本地排障包。确认的问题进入跨 agent 回放用例，检验状态延迟和错误等待/完成通知。不默认上传对话，也不让各端再造分类器。工作量中等，五端都受益。

### P1 — 按项目开工，五端使用同一套启动配置

**证据：** `internal/app/spawn.go` 已支持 cwd、agent、model、goal file 和 worktree；手机新建目前只打开主目录 shell，契约中尚无远程 spawn 接口。

**首批：** 在 Mac 配置项目与 agent 预设，手机选择项目、输入任务、确认目标 Mac 后开工。结构化 owner 请求复用 spawn 的就绪与回执机制；CLI、菜单栏、手机、iPad、网页共用预设。省去手动 cd、启动 agent 和重复选择配置，任务文本不拼成 shell 命令。工作量中等。

### P1 — HQ 任务从派发到交付、验收形成闭环

**证据：** `internal/dispatch/ledger.go` 已记录目标、送达和处置，`internal/hq/taskscmd.go` 关联实时状态；`radar.TaskStatusFor` 将 idle 映射为 done，注释明确含义是待审阅。relay 和 advice 也已有台账，应复用。

**首批：** 给任务关联结果摘要、PR/产物、验证证据，以及独立的「已验收／需返工」判断；pane 结束后仍能追踪同一任务。agent 一轮停下不等于目标已经通过验收。由用户或获授权的 HQ 判断，不能只凭 idle 自动结案。工作量中等，直接减少中控反复确认和结果丢失。

### P2 — HQ 授权范围与执行摘要清楚可见

**证据：** `internal/hq/hq.go` 通过章程和用户的 `LOCAL.md` 约束行为，relay 已明确保留用户决策权限。已有授权机制，主要以指令表达，并非完全没有权限设计。

**首批：** 展示当前允许事项、授权出处与预算；提供可审阅的观察汇报、常规回复、派发任务等预设，并记录 HQ 每次行动依据哪条规则。发布、删除与凭据不能因预设而默认为已授权。CLI 只能约束自身操作入口，不能仅靠一个配置就限制拥有任意 shell 能力的 agent，这个边界必须写清楚。工作量中到大，减少频繁确认与误用授权。

### P2 — 先衡量知识是否有用，再改善召回

**证据：** `openspec/specs/hq-knowledge/spec.md` 与 `internal/knowledge` 已有统一词法检索、派发时回显、出处与候选结算，不应再提一遍“增加搜索和来源记录”。

**首批：** 用真实任务建立应召回条目和不应召回条目的样例，记录任务使用了哪些知识、是否有帮助、冲突或被拒绝。先检验相关性、过期建议和缺失上下文，再决定语义检索或模型反思。推断与已核实证据分开，修正继续走现有台账。工作量中等，让 HQ 从存资料走向真正的贴身助手。

### P2 — 多台 Mac 的统一待处理列表

**证据：** `mobileapp/src/state/AppContext.tsx` 已保存多台 Mac、各自的通知选择，但只有一个 `activeUrl`，AgentsContext 跟随当前 Mac。

**首批：** 前台按用户选择汇总待处理事项，标明 Mac、任务和核实时间，离线项明确过期；点击后先切到正确 Mac，再打开 pane。不替换现有推送开关，也不默认在后台持续连接全部机器。工作量中等，优先服务真正同时管理多台 Mac 的用户。

### P2 — 项目工作集与恢复预览

**证据：** `internal/app/restore.go` 已有 CLI 选择、计划和 dry-run，`internal/resume` 已能恢复 agent 对话；档案迁移也已区分可迁移知识和本机状态。

**首批：** 保存命名的项目工作集，恢复前显示会接回哪些会话、在哪个目录、哪些条件不足。将选择恢复带到 app 与菜单栏，保留用户选择和本机前提，不把旧 Mac 的 board 当迁移知识恢复。工作量中到大，重启和换机时价值明显。

## 3. 配套工程与建议顺序

功能不能用时应明确原因：Mac 离线、访客权限、旧版服务或缺 tmux。可增加兼容旧版的操作能力接口，避免提交后才发现不支持。这是配套体验，不是产品的主要发展方向。

远程批量启动／恢复前，先补跨进程协调。`internal/state/runlock.go` 先读后写 PID 文件，写失败也视为拿到锁，只是辅助保护，不能保证互斥。后续应在隔离目录复现并发，再选择可靠锁。新建会话目前能在原会话存活时跨响应丢失和 serve 重启找回请求，但不保证多个 serve 同时创建或原会话销毁后的重试。未声称已证实用户发生重复恢复。

建议先做**状态可信 → 按项目开工 → HQ 交付验收**，随后推进授权与知识效果；多 Mac 与工作集按实际使用频率排序。保持同一个核心、状态语言和 Workspace，不为扩功能再造 iPad 流程或知识数据库。
