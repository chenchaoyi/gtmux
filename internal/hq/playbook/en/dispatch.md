# Dispatch, follow-up and reclaim

## Before assigning

Verify scope, existing driver and worker follow consent. Consult the maintenance runbook before advising or dispatching. Read the live digest and task receipts. Keep an existing pane's established purpose and verify the repository and `--cwd` before opening a worker. Plan independent, self-reporting steps, keep quick closeout separate from slow build/release work, and name the window/worktree for the task. Choose the agent and model explicitly for the task and budget. Use a lighter suitable model where available, narrow fan-out as quota or context tightens, and verify any compaction before depending on it.

Choose visible or background dispatch after applying LOCAL and the task's visibility needs. Use a background window only when appropriate. The installed `gtmux spawn` help describes `--headless` and `--oneshot`; interactive visibility and one-shot lifetime are separate decisions. DSH terminal uses the model chosen in its client, so omit generic `--model` and `--oneshot` there.

Use `gtmux spawn` with an explicit project directory and `--goal-file`. Write literal text safely, for example with a quoted heredoc `<<'EOF'`, since arguments are parsed by a shell. Include goal, scope, authority, expected evidence, reporting, storage and the applicable machine or project rules. Bind the exact workspace matter when present. Report the chosen agent/model and actual locator/title after dispatch. If dispatch fails, inspect its outcome and the existing task before retrying the supported path. Leave unrelated processes and state intact.

## Send, accept and follow up

Write the message file first. Fetch a fresh identity, activity and current instruction. For a working target, wait for its natural boundary or use an approved parallel worktree for unrelated work. A request to use an existing project lane does not authorize interrupting it. For a terminal target, use `tmux capture-pane -e` in a separate call. Keep the display attributes intact, read the result and decide whether to use a separate send call. For a nonterminal target, use its supported input check. An empty composer only clears the draft check. Keep a user's real draft intact, including one that arrives after the precheck. Treat an unclear screen or tool refusal as a hold. Do not send navigation keys, clear text, bypass with `--force`, or switch channels to evade a refusal. Use `gtmux send --message-file` or the workspace's tracked intent for authorized follow-up. For a form the tools cannot assess, focus the exact session for the user when appropriate.

Verify delivery with an exact receipt or the target's source history. A queued or uncertain submission remains pending while you reconcile the original attempt. Re-send only after confirming the original action did not land and checking current scope and input again. A receipt may prove submission before it proves work. Separate identity, receipt, work, result and acceptance. If a Stop promises future work, look for a live native goal, a scheduled completion callback, or a named driver. Keep active work undisturbed. Otherwise arrange a verified next step or explicit hold using the workspace runbook. A slash command, worker error or lost link alone does not establish completion. Report the observed result, unresolved gap and next owner.

## Resource limits and reclaim

Check disk, memory, CPU, battery and subscription limits before adding load. Hold high-write work at red disk. Coordinate a bounded low-write inventory, prioritize known regenerable and unused material within authorization and re-measure actual space. Route unresolved retention choices to the user. Avoid stale or repetitive suggestions. A low, draining battery needs a timely request to plug in. Use a real resource reading and current impact.

Normal reclaim follows verified completion and the relevant approval. Name the exact session, window, worktree and branch as applicable. Check title and identity, draft, ownership, running work, final evidence and retention constraints. Honor an existing approval or standing LOCAL rule within its exact scope. Request approval for uncovered irreversible action. Run `gtmux reap` or dispatch authorized cleanup, verify the resources actually removed and separately record remaining goal responsibility. On refusal, retain the work and use the supported snooze path. If a launch left an abandoned temporary window, determine ownership, ID and use before proposing or applying any applicable standing cleanup policy.
